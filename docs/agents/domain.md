## Сценарий

Пользователь вручную сохраняет выбранные изображения на отдельную доску Pinterest.
Сервис будет периодически проверять её через Playwright, скачивать новые изображения,
вести локальную очередь и рассчитывать даты публикаций. Затем Playwright будет
создавать отложенные публикации через веб-интерфейс MAX. В назначенное время
посты публикует сам MAX.

Интеграции выполняются через браузер: API Pinterest и MAX, IFTTT, сторонние сервисы
автоматизации и ручное скачивание изображений не входят в решение.

## Термины

- **Доска** — выбранный пользователем источник пинов Pinterest.
- **Пин / источник (`BoardPin`)** — подтверждённый элемент доски: Pin ID и URL,
  наблюдённые адреса изображения с signature либо отдельная ошибка материала.
  Источник существует и тогда, когда изображение получить не удалось.
- **Локальное изображение** — проверенный и атомарно сохранённый файл с SHA-256
  байтов, исходным URL изображения, MIME, размером и декодированными размерами.
  Результат `ready` относится к файлу, а не к заданию очереди.
  Разные пины могут давать одинаковые байты; визуальные копии после
  перекодирования могут иметь разные хеши.
- **Очередь** — локальные задания на подготовку отложенных публикаций.
- **Отложенная публикация** — пост, созданный в планировщике MAX на заданное время.

## Граница текущей реализации

Реализованы ручной вход Pinterest, полный обход, проверка файлов, постоянная
очередь SQLite, bootstrap, backfill и sync. Схема 5 хранит `board_state`, `pins`,
`images`, `queue`, `bootstrap_runs`, `backfill_runs`, `queue_events`, `max_attempts`; миграции
не обнуляют данные. Источники сохраняются независимо от файлов и заданий;
файл, ссылка источника и уникальное задание фиксируются одной транзакцией.
Pin ID и SHA-256 уникальны среди всех заданий, включая пропущенные.

`baseline` — история bootstrap/backfill; `candidate` — новый пин обычного sync.
Повторный обход не сбрасывает классификацию. До завершённого bootstrap или
полного обхода первоначального backfill sync отказывает до браузера. Bootstrap
не скачивает изображения и не создаёт заданий, сохраняет существующую очередь.
Частичный bootstrap сохраняет прогресс, но не подтверждает инициализацию.
Backfill обходит историю с начала, добавляя до N уникальных изображений;
дубликаты и отказы не расходуют N. Полный обход регистрирует оставшуюся историю
и подтверждает инициализацию даже при недоборе N. Задание и счётчик принятых
фиксируются атомарно. Resume с ID и прежним N продолжает ту же порцию;
без resume это новая порция. Оба sync полностью обходят доску, пропуская
baseline и известные файлы, сохраняя состояние и порядок заданий. Ошибки
кандидатов без файла допускают следующий sync; для истории нужен backfill.

Без команды запускается локальный `idle`. Команда `run` запускает независимые
циклы импорта Pinterest и MAX: сверку, расчёт дат и ограниченную последовательную
партию `scheduleMaxBatch`. CLI `plan --dry-run` только рассчитывает назначения.
Отдельной команды отправки нет. `auth max` проверяет настроенный канал и права
через UI с отдельным профилем; после проверки привязывает канал в `board_state`.
Подробности — в [README MAX](../../src/integrations/max/README.md). Существующие файлы и профили сохраняются.
Команды и воспроизводимый порядок запуска — в [README](../../README.md).

### Очередь и единственный владелец

```sh
npm start -- queue list
npm start -- queue skip <ID>
npm start -- queue retry <ID>
```

`queue list` открывает SQLite только для чтения, без миграций и браузера.
Он требует уже созданную схему импорта и возвращает согласованный JSON-снимок:
`items` с файлом и источником, `sources` включая отказы и ещё не обработанные пины,
`nextReadyId`, `board`, `bootstrapRuns`, `backfillRuns`, `queueEvents`, `maxAttempts`.
На старых поддерживаемых схемах часть истории отсутствует. `nextReadyId` —
выбор из снимка, не захват задания worker: самое раннее безопасное `ready`
по `added_at`, затем ID, без `max_post_url` и с наступившим `next_attempt_at`.
Отложенное время повтора одного задания не блокирует остальные готовые.

Импорт создаёт задания `ready`, пропуск переводит их в `skipped`.
`skip` разрешён только для `ready`/`failed` без известного внешнего поста.
`retry` разрешён только для `failed` без внешнего поста и возвращает его в `ready`.
Оба действия сохраняют ID, исходный порядок, файл и ошибку, очищают
`next_attempt_at` и атомарно добавляют прежнее состояние в `queue_events`.
`failed` источника не означает `failed` задания: отказ скачивания записывается
в `pins` без нового job и возобновляется импортом, а не `queue retry`.

`preparing`, `submitting`, `uncertain`, `scheduled` защищены от этих ручных
переходов. Продуктовая отправка использует эти состояния: перед единственным
финальным Send атомарно сохраняются `submitting` и намерение в `max_attempts`
(задание, канал, SHA-256, время, UUID). Ошибка после этой границы даёт
`uncertain`, без повторной отправки и переноса времени. Сверка может подтвердить
`scheduled` только по положительным однозначным доказательствам канала,
времени и изображения; отсутствие поста не разрешает повтор.
При старте `run` сохранённый `submitting` с попыткой переводится в `uncertain`
и также не разрешает повторное создание.

`scheduleMaxBatch` сначала сверяет `uncertain`, затем последовательно назначает
безопасные `ready`, перечитывая очередь и полную отложку перед каждым следующим
назначением. Определённый `failed` не расходует ёмкость и не блокирует другие
готовые задания; новый `uncertain` останавливает дальнейшие создания партии.
Партии запускает `run`; отдельной CLI-команды массовой отправки нет. Если время истекло до записи
намерения, слот занят или лимит исчерпан, задание возвращается в `ready`
для пересчёта; после границы намерения неподтверждённый исход — `uncertain`.

Непосредственно перед Send повторно проверяются канал, время, занятость и лимит.
Атомарной транзакции между SQLite и MAX нет: после проверки остаётся внешняя
гонка. Обнаруженное после отправки изменение метаданных чужих постов
останавливает следующие записи с диагностикой. Проверка не видит изменения
текста с сохранением признака его наличия или пикселей по прежнему media URL;
исключение всех внешних гонок не гарантируется.

`scheduled` — терминальное подтверждение создания отложки с evidence,
а не фактического выхода. Публикует MAX; исчезновение из отложки не отменяет
историю. В схеме 5 попытка и её исход сохраняются вместе с переходом задания.
Отправка и сверка используют общее подтверждение. Для изображения сначала
проверяются точные декодированные пиксели, затем —
нормализованное сравнение `area-rgb-32-v1` для изменений размера/кодирования
MAX. Это не криптографическая идентичность: тонкие изменения внутри ячейки
могут быть неразличимы. Нужны также единственный пост, точный канал и время.

### Расписание и браузерное время

`plan --dry-run` читает актуальную полную отложку MAX и предлагает назначения
FIFO в UTC и МСК, не мигрируя SQLite и не меняя очередь, файлы или посты.
Нужны привязка через `auth max` и явные `MAX_CHANNEL_URL`,
`PUBLICATION_SLOTS` (уникальные HH:mm через запятую без пробелов),
`MAX_SCHEDULED_LIMIT` (положительное целое). Горизонт
`PLANNING_HORIZON_DAYS` по умолчанию 14 календарных дней до того же московского
времени включительно. Используются только строго будущие слоты; все посты MAX,
включая ручные и находящиеся вне горизонта, занимают минуты и ёмкость.
Незавершённые локальные назначения учитываются консервативно: возможное
совпадение с постом MAX до положительной сверки считается дважды. Эффективный лимит —
минимум настроенного и документированного предела MAX 100; сотней постов его
не проверяли. План не резервирует места: отправка повторно читает MAX.

Все браузерные контексты MAX должны использовать `Europe/Moscow`:
интерфейс показывает время в зоне браузера, хранилище сохраняет UTC.
Сессии Pinterest и MAX раздельны. Потеря входа, CAPTCHA, прав или структуры
ставит на паузу затронутую интеграцию `run`; восстановление входа выполняется
вручную через `auth pinterest`/`auth max` после остановки процесса, без обхода
защиты. Неопределённый Send повтору не подлежит.

Все изменяющие команды, авторизация, live-скрипты и `idle` держат эксклюзивную
SQLite-транзакцию в отдельном `DATA_DIR/worker-lock.sqlite` всю операцию.
Второй владелец получает ошибку занятости до браузера и изменений состояния.
`plan --dry-run` тоже удерживает ownership для профиля MAX.
`queue list` и `--help` доступны без этого захвата. После SIGINT/SIGTERM,
ошибки или SIGKILL ОС освобождает захват: TTL и удаление lock-файла не нужны.
Не удаляйте его для обхода защиты; поддерживается локальная ФС одного узла.
Перед авторизацией или ручным импортом остановите `run` или `idle` с тем же `DATA_DIR`.


Pinterest-интеграция отвечает за браузер, селекторы, источники и скачивание;
внутренняя логика очереди и расписания не зависит от Pinterest.
Файлы скачиваются автоматически через Playwright по наблюдённым CDN-адресам,
без Pinterest API и конструирования предполагаемого URL исходника.

Полнота обхода требует стабильного счётчика, всех уникальных слотов и Pin ID,
`aria-busy=false` и наблюдённого маркера конца; рекомендации исключаются.
Пауза не доказывает конец, через 120 секунд без подтверждения возвращается
частичный результат. Полный список источников не означает успешную подготовку
всех файлов: ошибка материала сохраняется отдельно, а потеря доступа или структуры
останавливает браузерные действия. `summary.json` в `DATA_DIR/diagnostics/sync-*/`
разделяет итог обхода, готовые файлы, отказы и необработанные источники; неполная
синхронизация завершается с кодом 1.

Максимум изображения определяется декодированной площадью среди всех наблюдённых
вариантов. JPEG/PNG/WebP проверяются до атомарного сохранения через `.part`
с повторным SHA-256; перенаправления и тихая подмена отказавшего варианта
миниатюрой не разрешены. Побайтовый хеш не распознаёт визуальное сходство
и не подтверждает совместимость файла с MAX.

На 6 ноября 2026 года подтверждены обход реальной доски 166/166 и получение
максимального наблюдённого варианта одного пина 1289×1990. CLI до появления постоянной очереди сохранил
семь файлов, затем остановился с `structure-changed` на восьмом пине (код 1,
158 источников не обработаны). При дополнительном чтении отказ не воспроизведён;
точная причина и полный импорт файлов всей доски не подтверждены. На тот момент
публикации в MAX ещё не проверялись.

10 ноября отдельный исследовательский Playwright-сценарий подтвердил отложку,
её сохранность после перезапуска и фактическую публикацию одного фото в MAX.
Тестовый пост удалён, задание пропущено. Это исследовательский сценарий UI.
В той проверке backfill импортировал один файл, но завершил обход таймаутом
165/166 и кодом 1. Пустая отложка скрывает кнопку её открытия; текущий `auth max` больше
не требует её для подтверждения прав автора.

На том же авторизованном профиле отдельно проверены bootstrap (166/166,
без скачивания), backfill на одно изображение и resume того же ID с N=1:
все три завершились с кодом 0. Снимок после resume содержит прежнее единственное

повторно проверен. Это ограниченная проверка очереди, не полный импорт доски.

Позднее продуктовый `submitMaxPost` выполнил один Send: фото без текста
появилось в отложке на 12 ноября, 15:00 МСК. Автоматический исход сохранился

В последующей ограниченной реальной партии backfill одного изображения завершил

полный reader подтвердил пустую отложку. Задание 3 сохранилось `scheduled`
как история создания; прежние задания 1 (`scheduled` после manual review)
и 2 (`skipped`) не менялись. Профиль закрыт и ownership освобождён.
`.env` и рабочие настройки не менялись. Это проверка одного поста,
а не многопостовой live-партии или заполнения лимита 100.
Реальный `plan --dry-run` прошёл без изменения SQLite и семи изображений.
Локальный `run`, восстановление и повторы реализованы и проверены
контролируемыми тестами. Linux-контейнер и перенос авторизации проверены.

Полная готовность MVP не подтверждена.

## Рабочий цикл и восстановление

После ручного входа Pinterest явно выберите `bootstrap` или первоначальный
`backfill --count N`; инициализацию подтверждает только полный обход истории.
Настройте `MAX_CHANNEL_URL`, `PUBLICATION_SLOTS`, `MAX_SCHEDULED_LIMIT` и выполните
`auth max`, чтобы проверить доступ и привязать канал. Затем:

```sh
npm start -- run
```

`run` до открытия браузеров проверяет инициализацию и совпадение доски/канала
с хранилищем. Автоматического выбора истории нет. Импорт Pinterest и пополнение
MAX работают независимыми циклами: ожидание или пауза одного не мешают другому.
Внутри каждого цикла операции последовательны. MAX сначала сверяет `uncertain`,
затем рассчитывает и выполняет ограниченную партию безопасных `ready`.

`SYNC_INTERVAL_SECONDS` по умолчанию равен `300`; допустимы числа от `0.001`
до `2147483.647` секунды включительно. Интервал отсчитывается после операции.
Доказанные временные сетевые отказы допускают максимум пять повторов с растущей
задержкой: база — максимум настроенного интервала и 5 секунд, затем удвоение,
с ограничением таймера Node.js `2147483647` мс. Повтор не начинается раньше
настроенного интервала; успешный цикл сбрасывает серию сетевых отказов.
Истечение серии, потеря авторизации, CAPTCHA, неизвестный UI или другая
неподтверждённая ошибка ставят на паузу только затронутую интеграцию.

Для восстановления остановите `run` через Ctrl+C/SIGTERM, исправьте сеть или
локальную ошибку; при потере входа выполните `auth pinterest` либо `auth max`
для соответствующего сервиса, а при изменении UI сначала исправьте интеграцию.
После этого запустите `run` снова. CAPTCHA требует ручного восстановления
доступа без обхода защиты. Ошибка файла или диска сама по себе не требует входа.
Пауза не снимается автоматически в работающем процессе.

До намерения Send доказанный сетевой отказ MAX сохраняется как `failed`
с `next_attempt_at` и историей `max-network-delay`. Когда срок наступил,
`run` атомарно возвращает его в `ready` только при наличии этой истории,
без внешнего поста и без любой записи `max_attempts`; слот рассчитывается заново.
История ограничивает пять автоматических повторов задания и сохраняется после
перезапуска. После записи намерения исход остаётся `uncertain`: только сверка,
без повторного Send, переноса времени или принудительного `queue retry`.
Если сверка не дала однозначного положительного доказательства, сохраните
`uncertain` и разберите историю попытки и приватную диагностику вручную.
Отсутствие поста в текущей отложке не доказывает, что Send не состоялся.

После захвата ownership при старте `run` атомарно восстанавливает прерванные
состояния с записью `max-recovery`: безопасный `preparing` без внешнего поста
и попытки становится `ready`, его предварительное время и задержка очищаются;
`submitting` и сохранённая попытка становятся `uncertain` для сверки.
Другие небезопасные прерванные состояния также остаются `uncertain`.
Терминальные `scheduled`/`skipped` не меняются.

SIGINT/SIGTERM прекращает запуск новых операций, прерывает браузеры, сохраняет
известный исход текущей операции до диагностики и закрывает хранилище.
Возможный Send остаётся для сверки. SIGKILL не выполняет очистку приложения,
но ОС освобождает ownership; следующий `run` восстанавливает локальные состояния.
TTL и удаление `worker-lock.sqlite` не нужны.

Сохранённое в редакторе своё фото после аварии переиспользуется только при
пустом тексте, единственном вложении с точным именем `<sha256>.<jpg|png|webp>`
и точном совпадении декодированных пикселей с локальным файлом. Чужой или
неоднозначный черновик остаётся нетронутым; отправка прекращается.

Браузерные ошибки пишутся как JSON `browser-error`: `time`, `service`,
`operation`, доступный `jobId`, `code`, безопасный `reason`, `diagnostics`,
`screenshotAvailable`, путь `screenshot` при успехе и `diagnosticWritten` в логе.
`cycle-error` сообщает `paused` и `retryInMs`. Сырые `cause`, пароли, коды,
cookies и токены не сериализуются; адреса в причине скрываются.
Диагностика хранится локально вне Git: каталоги 0700, файлы 0600 на POSIX.
Неудача скриншота/диагностики явно отражается и не подменяет исходную причину.
Ошибка сохранения состояния останавливает затронутую интеграцию; для MAX
дальнейшие записи прекращаются до разбора диска и восстановления при старте.

Рабочий CLI проверен контролируемыми локальными сценариями; live-worker
`run` с новыми публикациями не запускался. Linux-контейнер и перенос авторизации
проверены; сквозная проверка worker этапа 7.3 отменена пользователем из-за
отсутствия прав записи в исходную доску. Полная готовность MVP не подтверждена.
