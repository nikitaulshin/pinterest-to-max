# Pinterest → MAX

Небольшой сервис для автоматизации публикаций изображений из Pinterest в канал MAX.
Пользователь вручную отбирает пины на отдельную доску. Рабочий цикл:
Playwright проверяет доску и скачивает новые изображения → локальная очередь
рассчитывает даты → Playwright создаёт отложенные посты в MAX → MAX публикует их.

**Сейчас реализованы импорт Pinterest, постоянная очередь и функции MAX:**
ручной вход, обход доски, bootstrap, ограниченный backfill, `sync [--full]`,
просмотр, пропуск и безопасный повтор задания; чтение отложки, создание одного
поста, сверка неопределённого исхода и ограниченная последовательная партия.
CLI `plan --dry-run` рассчитывает расписание без отправки, а `run` запускает
независимые циклы импорта и пополнения MAX с восстановлением очереди.
Без команды запускается `idle` до остановки. CLI проверен локально;
live-worker с новыми публикациями не запускался. Полный обход источников подтверждён;
полный импорт файлов всей доски пока нет.

## Архитектура

Один процесс Node.js 24, TypeScript/ESM, Playwright и встроенный `node:sqlite`.
Фреймворки, отдельный сервер БД, HTTP API и веб-интерфейс не требуются.
`node:sqlite` позволяет обойтись без ORM и нативного npm-модуля.
Другие основные версии Node.js требуют отдельной проверки совместимости.

```text
src/
  main.ts                     запуск, хранилище и завершение процесса
  cli.ts                      команды и конфигурация Pinterest/MAX
  run.ts                      независимые циклы, паузы и восстановление
  storage.ts                  SQLite, миграции, импорт и снимок очереди
  storage-ownership.ts        единственный владелец каталога данных
  core/                       FIFO, безопасные переходы и чистый расчёт расписания
  integrations/
    pinterest/                авторизация, обход, проверка и скачивание изображений
    max/                      авторизация, чтение, отправка, подтверждение и сверка
tests/smoke.test.ts            запуск собранного приложения отдельным процессом
docs/agents/domain.md         актуальный сценарий и доменные термины
openspec/                     существующий процесс работы с требованиями
```

`core/queue.ts` содержит правила FIFO и ручных переходов, без Playwright,
селекторов и SQLite. `storage.ts` применяет их в коротких транзакциях и хранит
источники отдельно от заданий. Pinterest-интеграция отвечает за браузер,
источники и локальные файлы; `main.ts` связывает её с CLI и хранилищем.
`core/planning.ts` рассчитывает будущие слоты и FIFO по полному снимку MAX.
MAX-интеграция содержит `submitMaxPost`, `reconcileMaxPost`, предпросмотр плана
и `scheduleMaxBatch`: сверку неопределённых попыток, расчёт и последовательную
отправку ограниченной партии. Вызывающий держит ownership и управляет ресурсами;
`run.ts` подключает партии и импорт к независимым циклам.

Интеграции работают только через Playwright: без API Pinterest/MAX,
IFTTT, сторонних сервисов автоматизации и ручного скачивания изображений.

## Локальный запуск

Нужны Node.js 24 LTS (от 24.15; основная версия зафиксирована в `.node-version`)
и npm. Команды выполняются из корня репозитория:

```sh
npm ci
cp .env.example .env
npm run build
npm start
```

Для разработки: `npm run dev` запускает исходный TypeScript со встроенным
наблюдением Node.js. TypeScript проверяется отдельной командой, не во время `dev`.
Остановка — Ctrl+C или SIGTERM; приложение закрывает SQLite и завершается с кодом 0.
Ошибка открытия хранилища или пустой `DATA_DIR` прерывают запуск с ненулевым кодом.

Для авторизации, синхронизации, live-проверок и браузерных тестов нужен браузер.
Chromium устанавливается отдельно:

```sh
npm run browser:install
```

На Linux системные библиотеки Chromium можно установить командой
`npx playwright install --with-deps chromium` (потребуются права администратора).
Для запуска без команды браузер не нужен. `npm test` и `npm run check` включают
браузерные DOM/CLI-сценарии и требуют установленного браузера, хотя эти тесты
не обращаются к настоящему Pinterest.
Вместо Chromium можно явно выбрать уже установленный Google Chrome:
`PINTEREST_BROWSER_CHANNEL=chrome`. Автоматической подмены браузера нет.

## Авторизация Pinterest и импорт

После сборки выполните в графическом окружении:

```sh
npm start -- auth pinterest
```

Команда открывает видимый браузер с отдельным постоянным профилем Pinterest.
Если требуется вход, введите пароль и код только на сайте и вернитесь на заданную
доску. CLI не запрашивает эти данные. Событие `authenticated` подтверждает доступ
к доске; после этого браузер закрывается. Повторный запуск использует сохранённую
сессию. При отсутствии доступа повторите вход; CAPTCHA/блокировка и неизвестная
структура страницы останавливают проверку без обхода защиты или угадывания селекторов.
На вход отведено до пяти минут. Перед запуском закройте процессы, использующие
этот профиль; один профиль нельзя одновременно открывать двумя браузерами.
Настройки MAX не нужны. Справка: `npm start -- --help`.

После авторизации явно выберите политику первоначальной истории:

```sh
# Зарегистрировать текущую доску без скачивания и новых заданий:
npm start -- bootstrap
# Либо импортировать порцию из одного уникального исторического изображения:
npm start -- backfill --count 1
```

Это альтернативы первоначального выбора; backfill допустим и после bootstrap.
`sync` и `sync --full` до инициализации истории отказывают до запуска браузера.
Bootstrap регистрирует пины как `baseline`, не скачивает изображения и не меняет
существующие задания. Только завершённый bootstrap подтверждает инициализацию;
частичный обход сохраняет прогресс, но требует нового запуска bootstrap.

Backfill обходит историю с начала доски, включая `baseline`, и добавляет до N
ещё не поставленных в очередь уникальных изображений в порядке обхода. Дубликаты
и отказы материалов не расходуют лимит. Полный обход подтверждает историю даже
при недоборе N; недобор или частичный обход дают код 1 с причиной и фактическим
числом принятых заданий. Лимит, принятое число и прогресс сохраняются в SQLite;
добавление задания и увеличение счётчика атомарны. Полный исторический набор
регистрируется даже при достижении N. Для продолжения используйте `runId` из
события `pinterest-sync-finished` или `backfillRuns` снимка очереди:

```sh
npm start -- queue list
npm start -- backfill --count 1 --resume <runId>
```

При resume требуется исходное N: исходный лимит не увеличивается, готовые задания
не повторяются. Без `--resume` каждый backfill означает новую порцию истории.
Даже возобновление завершённого запроса снова обходит доску, но не добавляет сверх N.

После инициализации импортируйте новые пины:

```sh
npm start -- sync
# Тот же полный обход, без остановки на известном пине:
npm start -- sync --full
```

Обе команды сначала читают доску, затем последовательно готовят ещё не
импортированные `candidate`. Исторические `baseline` пропускаются; очередь
известного пина не сбрасывается. Ошибка источника без готового файла допускает
следующую попытку sync, если источник не `baseline`; для истории нужен backfill.
Настройки MAX не нужны. В `DATA_DIR/images/` сохраняются проверенные файлы
`<sha256>.jpg`, `<sha256>.png` или `<sha256>.webp`. Уникальность заданий по Pin ID
и SHA-256 сохраняется и после пропуска: повторный импорт не создаёт новое место.
SHA-256 сравнивает байты, а не визуальное сходство перекодированных изображений.

Завершение обхода требует стабильного счётчика доски, покрытия всех уникальных
слотов `0…count−1` и Pin ID, `aria-busy=false` и появления блока других идей.
Рекомендации из `more-ideas-feed` исключаются. Пауза или одинаковые экраны
не доказывают конец; ожидание ограничено 120 секундами. Неизвестная структура,
изменение доски или счётчика дают частичный результат с уже прочитанными источниками.

Изображение выбирается по наибольшей декодированной площади среди наблюдённых
в DOM вариантов карточки и страницы пина; URL `originals` не конструируется.
Проверяются ответ, JPEG/PNG/WebP-контейнер и декодируемость; перенаправления
отклоняются. Недоступный вариант не подменяется миниатюрой. Сохранение идёт через
приватный `.part`, повторную проверку SHA-256 и атомарное переименование.
Результат подготовки `ready` означает проверенный локальный файл. Хранилище
атомарно связывает его с источником и создаёт задание `ready`, если уникальность
Pin ID и SHA-256 позволяет это. Совместимость с MAX этим не подтверждается.

Каждый запуск пишет приватный каталог `DATA_DIR/diagnostics/sync-<время>-<UUID>/`:

- `sources.json` — результат обхода и источники, если обход вернул результат;
- `results.jsonl` — результаты уже обработанных материалов, если обработка началась;
- `summary.json` — итог: `status`, `traversalStatus`, `traversalReason`, `expectedCount`,
  `observed`, `ready`, `known`, `materialFailures`, `browserFailures`, `unprocessed`, `browserStop`;
  `mode`, `runId` для bootstrap/backfill, а для backfill также `requestedCount`,
  `acceptedCount`, `shortfall`, `reason`;
- `error.png` — скриншот при ошибке, если его удалось сохранить;
  `screenshotAvailable` явно сообщает результат попытки.

JSON-событие `pinterest-sync-finished` содержит итог. Код 0 означает `complete`:
обход подтверждён и выполнено условие режима (bootstrap без скачивания, backfill
до N, sync без отказов материалов). `ready` в итогах считает результаты файлов,
а не новые задания: одинаковые байты могут дать один job. Код 1 означает
`incomplete` либо ошибку запуска. Ошибка отдельного материала сохраняется, обработка
продолжается; потеря доступа, CAPTCHA или неподтверждённая структура прекращают
дальнейшие браузерные действия. Полный обход не означает полный импорт файлов.

На 6 ноября 2026 года отдельная live-проверка подтвердила обход 166/166 источников.
Для пина `632263235234925609` сохранён и повторно декодирован наблюдённый
`originals` размером 1289×1990, SHA-256 сохранённых байтов совпал. Реальный CLI
`sync` до появления постоянной очереди также обошёл 166/166 источников, сохранил семь файлов и остановился на восьмом
пине с `structure-changed` (код 1; 158 источников не обработаны). Дополнительное
чтение восьмого пина не воспроизвело отказ; точная причина не установлена.
Полный импорт всех файлов и цепочка Pinterest → MAX не подтверждены.

На том же авторизованном профиле отдельно проверены bootstrap (166/166,
без скачивания), backfill на одно изображение и resume того же ID с N=1:
все три завершились с кодом 0. Снимок после resume содержит прежнее единственное
задание ready и 166 источников; новых файлов resume не скачивал. SHA-256 файла
повторно проверен. Это ограниченная проверка очереди, не полный импорт доски.

Отдельные явные проверки после авторизации:

```sh
node --env-file-if-exists=.env scripts/check-pinterest-pin.ts
node --env-file-if-exists=.env scripts/check-pinterest-board.ts
node --env-file-if-exists=.env scripts/check-pinterest-image.ts
```

Они открывают видимый браузер с тем же профилем. Первая читает один пин без
скачивания (`pin-<время>/{pin.json,pin.png}`), вторая проверяет только обход
(`board-<время>/{board.json,board.png}`), третья скачивает изображение первого пина
и перепроверяет файл (`image-<время>/{image.json,decode.json,pin.png}`). Все каталоги
находятся в `DATA_DIR/diagnostics/`. При ошибках скрипты пытаются сохранить
`error.png`; диагностика может содержать приватные данные.

## Авторизация MAX

Укажите `MAX_CHANNEL_URL` явно и выполните `npm start -- auth max`.
Команда открывает отдельный профиль `DATA_DIR/profiles/max`; при необходимости
задайте `MAX_BROWSER_CHANNEL=chrome`, по умолчанию используется Playwright Chromium.
Вход выполняется вручную только на сайте. После проверки точной ссылки канала
в его профиле и прав публикации сохраняется привязка канала в SQLite.
Повторный запуск использует сохранённую сессию, смена привязанного канала запрещена.
Pinterest не запускается; существующие доска, очередь и профиль сохраняются.
Для нового хранилища используется `PINTEREST_BOARD_URL` либо стандартная доска.
Публикации не создаются. Подробности и граница проверки — в
[README интеграции MAX](src/integrations/max/README.md).

## Предпросмотр расписания

После импорта и `auth max` задайте в `.env` явные `MAX_CHANNEL_URL`,
`PUBLICATION_SLOTS` (например, `09:00,15:00`) и `MAX_SCHEDULED_LIMIT`
(например, `10`), затем выполните:

```sh
npm start -- plan --dry-run
```

Команда использует сохранённую сессию MAX в headless-браузере с зоной
`Europe/Moscow`, читает полную актуальную отложку, включая ручные посты,
и предлагает будущие назначения FIFO в UTC и МСК. Горизонт по умолчанию —
14 календарных дней от момента расчёта до того же московского времени
включительно; начало строго в будущем. `PUBLICATION_SLOTS` — непустой список
уникальных `HH:mm` через запятую без пробелов. Прошлые слоты не переносятся
на немедленную публикацию. Занятость считается с точностью до минуты.
Все посты MAX, включая ручные и находящиеся вне горизонта, расходуют ёмкость.
Незавершённые локальные назначения также учитываются консервативно:
до положительной сверки возможное совпадение с постом MAX считается дважды. Эффективный
лимит — минимум настроенного и 100: это документированное ограничение MAX,
а не результат заполнения отложки сотней тестовых постов.

Dry-run не мигрирует SQLite, не сохраняет назначения, не меняет очередь,
изображения или посты; браузерный профиль, ownership и диагностика используются.
Отсутствие доступа или неполный снимок останавливают расчёт. Вывод — снимок,
а не резервирование: перед реальной отправкой требуется новое чтение MAX.
Отправку и сверку выполняет `run`; отдельной команды отправки нет.

### Ограниченная партия и граница отправки

Внутренняя `scheduleMaxBatch` сначала сверяет `uncertain`, затем распределяет
безопасные `ready` по FIFO (`added_at`, затем ID). Перед каждым следующим
назначением заново читаются очередь и полная отложка. Определённый отказ `failed`
не расходует место и не блокирует остальные готовые задания. Новый `uncertain`
останавливает дальнейшие создания текущей партии; повторный Send запрещён.
Отдельной CLI-команды массовой отправки нет; партии вызывает `run`.

Перед финальным Send повторно проверяются канал, время, занятость и лимит.
Если слот занят, ёмкость исчерпана или время истекло до записи намерения,
задание возвращается в `ready` для нового расчёта. После атомарной локальной
записи `submitting` и попытки любой неподтверждённый исход остаётся `uncertain`.
Сверка подтверждает существующий пост без повторной отправки только по
единственному совпадению канала, времени, пустого текста и изображения.
Отсутствие поста или истёкшее время не разрешают повтор или перенос назначения.

Отправка и сверка используют общее подтверждение изображения: точные
декодированные пиксели, затем нормализацию `area-rgb-32-v1`, если MAX изменил
размеры или кодирование. Это не криптографическая идентичность: тонкие изменения
внутри ячейки могут быть неразличимы. Алгоритм применяется вместе с каналом,
временем и единственным подходящим постом.

Между последней проверкой и Send остаётся внешняя гонка: общей атомарной
транзакции с MAX нет. Обнаруженное после отправки изменение метаданных чужих
постов останавливает следующие записи с диагностикой. Такая проверка не
обнаруживает изменение текста с сохранением признака его наличия или замену
пикселей по прежнему media URL. Она не гарантирует исключения любой внешней гонки.

10 ноября ограниченная реальная партия после backfill одного изображения
(полный обход 165/165) выполнила ровно один Send для задания 3 на 11 ноября,
15:00 МСК. Исход был `uncertain` из-за неподдержанного заголовка «Завтра».
После исправления reader продуктовая сверка автоматически подтвердила ту же
попытку как `scheduled` без нового Send; повторное чтение подтвердило один пост.
Собственный тест удалён, после reload отложка подтверждена пустой, профиль закрыт
и ownership освобождён. Это отдельная проверка от прежнего ручного разбора
исторических доказательств задания 1. `.env` и рабочие настройки не менялись.
Один пост не проверяет многопостовую live-партию или заполнение лимита 100.
Linux-контейнер и перенос авторизации проверены. Сквозная проверка worker
этапа 7.3 отменена пользователем из-за отсутствия прав записи в исходную доску.
Полная готовность MVP не подтверждена. Локальный `run` проверен тестами.

## Очередь и единственный владелец

```sh
npm start -- queue list
npm start -- queue skip <ID>
npm start -- queue retry <ID>
```

`queue list` открывает SQLite только для чтения, без миграций и браузера.
Он требует уже созданную схему импорта и возвращает согласованный JSON-снимок:
`items` с файлом и источником, `sources` включая отказы и ещё не обработанные пины,
`nextReadyId`, `board`, `bootstrapRuns`, `backfillRuns`, `queueEvents`, `maxAttempts`.
На старых поддерживаемых схемах часть истории отсутствует. `nextReadyId` —
выбор из снимка, не захват задания worker: самое раннее безопасное `ready`
по `added_at`, затем ID, без `max_post_url` и с наступившим `next_attempt_at`.
Отложенное время повтора одного задания не блокирует остальные готовые.

Импорт создаёт задания `ready`, пропуск переводит их в `skipped`.
`skip` разрешён только для `ready`/`failed` без известного внешнего поста.
`retry` разрешён только для `failed` без внешнего поста и возвращает его в `ready`.
Оба действия сохраняют ID, исходный порядок, файл и ошибку, очищают
`next_attempt_at` и атомарно добавляют прежнее состояние в `queue_events`.
`failed` источника не означает `failed` задания: отказ скачивания записывается
в `pins` без нового job и возобновляется импортом, а не `queue retry`.

`preparing`, `submitting`, `uncertain`, `scheduled` защищены от этих ручных
переходов. Продуктовая отправка создаёт эти состояния: перед единственным
финальным Send атомарно сохраняются `submitting` и намерение в `max_attempts`.
Ошибка после этой границы даёт `uncertain`: повторная отправка запрещена,
разрешена только сверка. `scheduled` означает подтверждённое создание отложки,
а фактическую публикацию в назначенное время выполняет MAX. Сохранённое
подтверждение не отменяется из-за исчезновения поста из отложки. Восстановление
незавершённых состояний выполняется при старте `run` после захвата ownership.

Все изменяющие команды, авторизация, live-скрипты и `idle` держат эксклюзивную
SQLite-транзакцию в отдельном `DATA_DIR/worker-lock.sqlite` всю операцию.
Второй владелец получает ошибку занятости до браузера и изменений состояния.
`plan --dry-run` также удерживает ownership ради профиля MAX; очередь он не меняет.
`queue list` и `--help` доступны без этого захвата. После SIGINT/SIGTERM,
ошибки или SIGKILL ОС освобождает захват: TTL и удаление lock-файла не нужны.
Не удаляйте его для обхода защиты; поддерживается локальная ФС одного узла.
Перед авторизацией или ручным импортом остановите `run` или `idle` с тем же `DATA_DIR`.

## Рабочий цикл и восстановление

После ручного входа Pinterest явно выберите `bootstrap` или первоначальный
`backfill --count N`; инициализацию подтверждает только полный обход истории.
Настройте `MAX_CHANNEL_URL`, `PUBLICATION_SLOTS`, `MAX_SCHEDULED_LIMIT` и выполните
`auth max`, чтобы проверить доступ и привязать канал. Затем:

```sh
npm start -- run
```

`run` до открытия браузеров проверяет инициализацию и совпадение доски/канала
с хранилищем. Автоматического выбора истории нет. Импорт Pinterest и пополнение
MAX работают независимыми циклами: ожидание или пауза одного не мешают другому.
Внутри каждого цикла операции последовательны. MAX сначала сверяет `uncertain`,
затем рассчитывает и выполняет ограниченную партию безопасных `ready`.

`SYNC_INTERVAL_SECONDS` по умолчанию равен `300`; допустимы числа от `0.001`
до `2147483.647` секунды включительно. Интервал отсчитывается после операции.
Доказанные временные сетевые отказы допускают максимум пять повторов с растущей
задержкой: база — максимум настроенного интервала и 5 секунд, затем удвоение,
с ограничением таймера Node.js `2147483647` мс. Повтор не начинается раньше
настроенного интервала; успешный цикл сбрасывает серию сетевых отказов.
Истечение серии, потеря авторизации, CAPTCHA, неизвестный UI или другая
неподтверждённая ошибка ставят на паузу только затронутую интеграцию.

Для восстановления остановите `run` через Ctrl+C/SIGTERM, исправьте сеть или
локальную ошибку; при потере входа выполните `auth pinterest` либо `auth max`
для соответствующего сервиса, а при изменении UI сначала исправьте интеграцию.
После этого запустите `run` снова. CAPTCHA требует ручного восстановления
доступа без обхода защиты. Ошибка файла или диска сама по себе не требует входа.
Пауза не снимается автоматически в работающем процессе.

До намерения Send доказанный сетевой отказ MAX сохраняется как `failed`
с `next_attempt_at` и историей `max-network-delay`. Когда срок наступил,
`run` атомарно возвращает его в `ready` только при наличии этой истории,
без внешнего поста и без любой записи `max_attempts`; слот рассчитывается заново.
История ограничивает пять автоматических повторов задания и сохраняется после
перезапуска. После записи намерения исход остаётся `uncertain`: только сверка,
без повторного Send, переноса времени или принудительного `queue retry`.
Если сверка не дала однозначного положительного доказательства, сохраните
`uncertain` и разберите историю попытки и приватную диагностику вручную.
Отсутствие поста в текущей отложке не доказывает, что Send не состоялся.

После захвата ownership при старте `run` атомарно восстанавливает прерванные
состояния с записью `max-recovery`: безопасный `preparing` без внешнего поста
и попытки становится `ready`, его предварительное время и задержка очищаются;
`submitting` и сохранённая попытка становятся `uncertain` для сверки.
Другие небезопасные прерванные состояния также остаются `uncertain`.
Терминальные `scheduled`/`skipped` не меняются.

SIGINT/SIGTERM прекращает запуск новых операций, прерывает браузеры, сохраняет
известный исход текущей операции до диагностики и закрывает хранилище.
Возможный Send остаётся для сверки. SIGKILL не выполняет очистку приложения,
но ОС освобождает ownership; следующий `run` восстанавливает локальные состояния.
TTL и удаление `worker-lock.sqlite` не нужны.

Сохранённое в редакторе своё фото после аварии переиспользуется только при
пустом тексте, единственном вложении с точным именем `<sha256>.<jpg|png|webp>`
и точном совпадении декодированных пикселей с локальным файлом. Чужой или
неоднозначный черновик остаётся нетронутым; отправка прекращается.

Браузерные ошибки пишутся как JSON `browser-error`: `time`, `service`,
`operation`, доступный `jobId`, `code`, безопасный `reason`, `diagnostics`,
`screenshotAvailable`, путь `screenshot` при успехе и `diagnosticWritten` в логе.
`cycle-error` сообщает `paused` и `retryInMs`. Сырые `cause`, пароли, коды,
cookies и токены не сериализуются; адреса в причине скрываются.
Диагностика хранится локально вне Git: каталоги 0700, файлы 0600 на POSIX.
Неудача скриншота/диагностики явно отражается и не подменяет исходную причину.
Ошибка сохранения состояния останавливает затронутую интеграцию; для MAX
дальнейшие записи прекращаются до разбора диска и восстановления при старте.

Рабочий CLI проверен локальными сценариями. В этапе 7.1 подтверждены Linux
Chromium, чтение копии очереди и повторное открытие обеих сессий без отправки.
Сквозная проверка worker с новым пином и отсутствием дублей в этапе 7.3
отменена пользователем из-за отсутствия прав записи в исходную доску.
Полная готовность MVP не подтверждена.

(на системах с POSIX-правами). Для диагностики права также исправляются на 0700/0600 при записи;
права остальных уже существующих файлов не меняются.
Профили содержат доступ к учётным записям: не коммитьте их и не публикуйте
резервные копии. `.gitignore` исключает данные, базы, профили и `.env`.
При смене `DATA_DIR` храните данные вне отслеживаемых каталогов либо добавьте
свой путь в локальный `.git/info/exclude`.

## Docker Compose

Нужен рабочий Docker Engine с Compose и инструментами сборки. При переходе
с Docker Desktop на Colima проверьте, что Docker CLI не ссылается на удалённый
`docker-credential-desktop` и видит установленные плагины сборки.

```sh
docker compose config --quiet
docker compose build app
```

До запуска worker подготовьте том и сессии ниже. Если buildx отсутствует, проверен
классический builder: `DOCKER_BUILDKIT=0 docker build -t pinterest-to-max-app .`.
Образ использует Node.js 24 и `ENTRYPOINT ["node", "dist/main.js"]`;
Compose передаёт аргумент `run`. UID пользователя `node` — 1000.

Образ устанавливает Chromium и его системные библиотеки из версии Playwright,
закреплённой в `package-lock.json`. Приложение работает от пользователя `node`.
Включён init-процесс для сигналов и дочерних процессов браузера.

Compose хранит данные в именованном томе `app-data`, смонтированном в `/app/data`.
Ему не нужен локальный `.env`; `DATA_DIR` задан внутри контейнера. Локальный запуск
и Compose используют разные хранилища: старый `DATA_DIR` не переносится
автоматически. Сохраняйте имя проекта Compose: от него зависит имя тома.
`docker compose down` сохраняет том;
`docker compose down -v` удалит его вместе с данными и авторизацией.
Порты наружу не открываются. Compose запускает `run`; обязательные
`MAX_CHANNEL_URL`, `PUBLICATION_SLOTS`, `MAX_SCHEDULED_LIMIT` передаются из
окружения/`.env`, необязательные настройки доски, горизонта и интервала имеют
те же значения по умолчанию, что CLI. Оба браузера в контейнере явно используют
установленный Chromium, даже если на хосте выбран Chrome. Команда Compose
переопределяет аргументы CLI: например, `docker compose run --rm app --help`
или `docker compose run --rm app queue list`. Пустые обязательные настройки
отклоняет сам `run`, поэтому справка и импорт доступны без настроек планирования.

### Перенос авторизации в Linux

Остановите всех владельцев исходного и целевого каталогов данных. Сохраните
исходные данные; переносите копию в отдельный постоянный том, а не в образ.
SQLite копируйте через `node:sqlite` `backup` либо вместе с согласованным WAL;
не заменяйте рабочую БД старой копией после внешних публикаций. Изображения,
диагностику и раздельные `profiles/pinterest`, `profiles/max` сохраняйте.
Операции копирования и работы с браузером должны удерживать
`acquireStorageOwnership(DATA_DIR)` из `dist/storage-ownership.js`;
`worker-lock.sqlite` исходного каталога не удаляйте.

10 ноября 2026 года копия профиля MAX из macOS Chrome подтвердила доступ
к настроенному каналу через Linux Chromium. Для Pinterest простая копия
не подтвердила доступ: потребовалось стандартное состояние Playwright.
Для Pinterest предусмотрен отдельный сценарий без навигации и публикаций.
На хосте (Node.js 24, после `npm ci` и `npm run build`) сначала выполните
согласованное копирование из следующего раздела, затем экспортируйте состояние копии:

```sh
DATA_DIR="$TRANSFER_DIR/snapshot" PINTEREST_BROWSER_CHANNEL=chrome \
  node scripts/pinterest-session-state.ts export "$TRANSFER_DIR/storage-state-pinterest.json"
```

Если исходный профиль создан Chromium, явно укажите `chromium` вместо `chrome`.
Экспорт удерживает ownership, сохраняет cookies, localStorage и IndexedDB через
стандартный Playwright `storageState`, создаёт файл 0600 без перезаписи.
Пароли, cookies и содержимое состояния в лог не выводятся. MAX этот сценарий
не открывает: для проверенного профиля MAX достаточно копирования.
После подготовки согласованной копии данных в томе импортируйте Pinterest:

```sh
docker compose run --rm --entrypoint node app scripts/pinterest-session-state.ts import /app/data/storage-state-pinterest.json
```

`create` при подготовке ниже не запускает worker; все контейнеры с этим томом перед импортом должны
быть остановлены. Импорт использует Linux Chromium, ownership и стандартный
`setStorageState`; закрывает persistent context без удаления профиля. Он
заменяет браузерное состояние Pinterest по явному запросу, но не обнуляет
каталог профиля, БД и профиль MAX. Файл содержит секреты: не включайте его
в Git или образ; после подтверждения переноса удалите только эти временные
экспорты. Владельцы профилей и исходные данные должны оставаться сохранными.

Перед `run` повторно откройте оба профиля в Linux без импорта состояния
и подтвердите доступ только чтением целевой доски и канала. Так проверены
обе подготовленные сессии; отправка постов при этой проверке не выполнялась.
Если доступ не подтверждён, запуск блокируется до ручного входа в совместимом
графическом окружении: перенос профиля сам по себе не доказывает авторизацию.
В контейнере нет GUI/VNC, поэтому `auth` с видимым браузером требует хоста
с графическим окружением. Профили и файл состояния нельзя открывать параллельно
с работающим владельцем, публиковать или включать в образ.

### Подготовка пустого тома

Порядок: копия → экспорт Pinterest → заполнение пустого тома → импорт Pinterest →
повторное чтение сессий → dry-run → `run`. Не копируйте активный профиль.
Остановите всех владельцев исходного и целевого каталогов. Переменные
`SOURCE_DATA_DIR`/`TRANSFER_DIR` ниже нужны оператору, это не настройки приложения.

```sh
docker compose stop app
export SOURCE_DATA_DIR=/абсолютный/путь/к/существующим/данным
export TRANSFER_DIR="$(mktemp -d /tmp/pinterest-transfer.XXXXXX)"
node --input-type=module - <<'JS'
import { mkdirSync, cpSync, existsSync } from 'node:fs';
import { join } from 'node:path';
import { DatabaseSync, backup } from 'node:sqlite';
import { acquireStorageOwnership } from './dist/storage-ownership.js';
process.umask(0o077);
const source = process.env.SOURCE_DATA_DIR;
const target = join(process.env.TRANSFER_DIR, 'snapshot');
const release = acquireStorageOwnership(source);
try {
  mkdirSync(target, { mode: 0o700 });
  const database = new DatabaseSync(join(source, 'state.sqlite'), { readOnly: true });
  try { await backup(database, join(target, 'state.sqlite')); }
  finally { database.close(); }
  for (const name of ['images', 'profiles', 'diagnostics']) {
    if (existsSync(join(source, name))) cpSync(join(source, name), join(target, name), { recursive: true });
  }
} finally { release(); }
JS
```

`backup` включает подтверждённые записи WAL: одного файла `state.sqlite` при наличии
WAL недостаточно. Ownership удерживается на всём копировании. Не восстанавливайте
старую БД после внешнего намерения Send: потеря истории попытки допускает дубль.
После переноса используйте только один рабочий том для канала. Не запускайте
старый хостовый `DATA_DIR` параллельно: ownership защищает один каталог,
а не разные копии состояния одного канала. Источник сохраните как приватную копию.

Выполните экспорт Pinterest из предыдущего раздела, затем заполните **пустой** том.
Следующая команда держит ownership, отказывает при существующих данных и задаёт
владельца `node`:

```sh
docker compose create app
docker compose cp "$TRANSFER_DIR" app:/app/data/.transfer
docker compose run --rm -T --user root --entrypoint node app --input-type=module - <<'JS'
import { cpSync, existsSync, readdirSync, chmodSync } from 'node:fs';
import { join } from 'node:path';
import { execFileSync } from 'node:child_process';
import { acquireStorageOwnership } from './dist/storage-ownership.js';
process.umask(0o077);
const target = '/app/data';
const release = acquireStorageOwnership(target);
try {
```

Теперь выполните импорт Pinterest из предыдущего раздела. Импорт проверяет
принадлежность состояния только Pinterest. Экспорты храните вне репозитория либо
в игнорируемом `DATA_DIR` под именем `storage-state*.json`. Приватные данные
исключены из Git и build context; произвольный нестандартный `DATA_DIR` внутри
репозитория исключайте дополнительно **из обоих** контекстов либо выносите наружу.
Ignore не удаляет уже отслеживаемые секреты из истории Git.
Каталог `.transfer` содержит приватную промежуточную копию; после успешной проверки
удалите только эту копию и временные экспорты. `compose cp` не требует общего
bind-каталога между хостом и VM Docker, в отличие от `-v /tmp/...`.

### Повторное чтение сессий и запуск

Следующий блок выполните дважды без нового импорта. Он открывает и закрывает
Linux Chromium, читает доступ к доске/каналу без скачивания пинов и отправки.
Браузеры могут обновлять собственное состояние профилей; очередь и БД не меняются.

```sh
docker compose run --rm -T --entrypoint node app --input-type=module - <<'JS'
import { chromium } from 'playwright';
import { acquireStorageOwnership } from './dist/storage-ownership.js';
import { readBoardAccess } from './dist/integrations/pinterest/session.js';
import { openMaxChannel, readChannelAccess } from './dist/integrations/max/session.js';
const release = acquireStorageOwnership('/app/data');
try {
  for (const service of ['pinterest', 'max']) {
    const context = await chromium.launchPersistentContext(`/app/data/profiles/${service}`, {
      headless: true, timezoneId: 'Europe/Moscow',
    });
    try {
      const page = context.pages()[0] ?? await context.newPage();
      const url = process.env[service === 'pinterest' ? 'PINTEREST_BOARD_URL' : 'MAX_CHANNEL_URL'];
      if (service === 'pinterest') await page.goto(url, { waitUntil: 'domcontentloaded', timeout: 60000 });
      else await openMaxChannel(page, url);
      let access = 'unknown';
      let profileOpened = false;
      for (let attempt = 0; attempt < 40; attempt++) {
        access = service === 'pinterest' ? await readBoardAccess(page, url) : await readChannelAccess(page, url);
        if (access !== 'unknown') break;
        if (service === 'max' && !profileOpened) {
          const profile = page.getByRole('button', { name: /^Открыть профиль / });
          if (await profile.count() === 1 && await profile.isVisible()) {
            await profile.click();
            profileOpened = true;
          }
        }
        await page.waitForTimeout(500);
      }
      console.log(JSON.stringify({ service, access }));
      if (access !== 'ready') throw new Error('Read-only access was not confirmed.');
    } finally { await context.close(); }
  }
} finally { release(); }
JS
```

Оба результата должны быть `ready`; иначе worker запускать нельзя.
История должна быть явно инициализирована выбранным ранее `bootstrap` либо
`backfill --count N`; автоматического выбора нет. Укажите свои обязательные
канал, слоты и лимит. Предпросмотр:

```sh
docker compose run --rm app queue list
docker compose run --rm app plan --dry-run
```

Следующая команда **включает автоматический импорт и отправку в MAX**:

```sh
docker compose up -d app
docker compose logs -f app
```

Остановка и пересоздание с тем же проектом сохраняют том:

```sh
docker compose stop app
docker compose down
docker compose up -d app
```

Не добавляйте `-v` к `down`: удаление данных и авторизаций не является шагом
обновления. Перед обновлением остановите владельцев, сохраните согласованную копию,
затем пересоберите образ и пересоздайте контейнер с прежним томом.

В этапе 7.1 проверены Linux Chromium от UID 1000, чтение копии очереди, перенос
Pinterest и повторное открытие обеих сессий (`ready`) без публикаций. В этапе 7.3
проверена сохранность данных при остановке и пересоздании контейнера с `idle`.
Полная цепочка «новый пин → файл → очередь → подтверждённая отложка» и отсутствие
дублей после перезапуска worker не проверены: пользователь отменил внешний
сценарий из-за отсутствия прав записи в исходную доску.
