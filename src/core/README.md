# Внутренняя логика

`queue.ts` содержит правила задания и FIFO без Playwright, селекторов, Pinterest
и SQLite. Хранение и атомарные изменения находятся в `../storage.ts`, браузер
и подготовка файлов — в `../integrations/pinterest/`.

`QueueJob` создаётся через конструктор. Пропуск разрешён для ready/failed
без внешнего поста, повтор — только для failed без поста с возвратом в ready.
Preparing/submitting/uncertain/scheduled защищены; uncertain требует сверки MAX.
Эти состояния используются продуктовой отправкой MAX. Хранилище
записывает прежнее состояние в queue_events, сохраняет ошибку, ID, файл
и исходное место задания, очищая next_attempt_at при ручном переходе.

`nextReadyJob` выбирает ready без max_post_url с наступившим временем повтора,
по added_at, затем ID.
В queue list результат возвращается как nextReadyId из read-only снимка;
это не захват задания. `failed` и отложенный повтор не блокируют другие ready.

`planning.ts` содержит `PublicationSchedule` и `PublicationPlanner`, без браузера
и хранения. Нужны уникальные ежедневные `HH:mm` по `Europe/Moscow`, положительные
горизонт и явный лимит. Горизонт по умолчанию — 14 календарных дней до того же
московского времени включительно; назначаются только строго будущие слоты.
Планировщик сопоставляет FIFO с ближайшими свободными минутами полного снимка.
Эффективный лимит — минимум настройки и 100. Все посты, включая ручные вне
горизонта, расходуют ёмкость. `preparing`/`submitting`/`uncertain` резервируют
минуту и дополнительное место: возможное совпадение с постом считается дважды
до положительной сверки. План ничего не сохраняет и не резервирует.

CLI `plan --dry-run` читает SQLite без миграций и актуальную отложку MAX,
выводит времена UTC/МСК и ограничения без изменения очереди, файлов или постов;
ownership, браузерный профиль и диагностика используются. Внутренняя
`scheduleMaxBatch` в интеграции MAX сверяет uncertain и последовательно
выполняет ограниченную партию с повторным чтением перед каждым назначением.
`../run.ts` вызывает её в независимом от Pinterest цикле; отдельной команды
массовой отправки нет. `retry.ts` ограничивает безопасные сетевые повторы.

Истёкшее время до записи намерения, занятый слот или исчерпанная ёмкость
возвращают задание в ready для пересчёта. Перед Send атомарно сохраняются
submitting и попытка; неподтверждённый исход после этой границы — uncertain,
без повторной отправки и переноса. Сверка использует то же подтверждение,
что отправка: канал, время, единственный пост без текста и изображение
(точные пиксели либо `area-rgb-32-v1`). Нормализация не криптографическая:
тонкие изменения внутри ячейки могут быть неразличимы.

Новый uncertain или обнаруженная после последней проверки внешняя гонка
останавливают дальнейшие записи партии. Общей транзакции с MAX нет;
сравнение метаданных не видит изменения пикселей по прежнему media URL
или текста с сохранением признака его наличия. После захвата ownership `run`
атомарно восстанавливает безопасный preparing без попытки в ready с очисткой
предварительного времени, а submitting и попытку — в uncertain для сверки.
Терминальные состояния не меняются; SIGKILL освобождает ownership силами ОС.
Доказанный сетевой failed до намерения получает next_attempt_at и историю;
возврат в ready допускается только в срок, с provenance и без max_attempts.
После намерения возможна только сверка, без автоматического повторного Send.

Источник и файл отделены от задания: failed источника при скачивании не создаёт
job и не исправляется через queue retry. Дедупликация Pin ID/SHA-256, история
bootstrap/backfill и единственный владелец DATA_DIR обеспечиваются хранилищем
и точкой запуска. Хеш сравнивает байты, а не визуальное сходство.

в [доменном контексте](../../docs/agents/domain.md).
