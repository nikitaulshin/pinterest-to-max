# Pinterest

Реализованы ручная авторизация, полный обход доски и подготовка локальных
изображений через Playwright. API Pinterest не используется. Команды выполняются из корня
репозитория с Node.js 24 после `npm ci` и `npm run build`.

## Вход

```sh
npm run browser:install
npm start -- auth pinterest
```

Нужно графическое окружение. Браузер открывает доску из `PINTEREST_BOARD_URL`
(по умолчанию `https://ru.pinterest.com/mixi56453/max7`). Пароль и код вводятся
только на сайте; после входа нужно вернуться на доску. Команда ждёт до пяти минут,
проверяет доступ, выводит `authenticated` и закрывает браузер. Повторный запуск
использует постоянный профиль `DATA_DIR/profiles/pinterest` (`DATA_DIR=./data`
по умолчанию). Профиль Pinterest отделён от `profiles/max`; настройки MAX не нужны.

`PINTEREST_BROWSER_CHANNEL=chromium` использует установленный Playwright Chromium.
Значение `chrome` явно выбирает уже установленный Google Chrome; автоматического
fallback нет. Перед запуском закройте владельца профиля: одновременно открывать
один профиль двумя браузерами нельзя. Отсутствие доступа требует ручного входа;
CAPTCHA/блокировка и неподтверждённая структура останавливают операцию.

## Извлечение одного пина

После успешного входа:

```sh
node --env-file-if-exists=.env scripts/check-pinterest-pin.ts
```

Проверка использует те же настройки и профиль, читает первую подтверждённую
карточку сетки доски и открывает её страницу. Она возвращает Pin ID, URL пина
и наблюдённые в DOM варианты изображения (`src`, `currentSrc`, `srcset`). Адреса
не конструируются; рекомендации страницы пина не включаются в результат.
Неизвестная или неоднозначная разметка приводит к ошибке без запасного селектора.

Успех обозначается событием `pinterest-pin-verified`. Метаданные `pin.json`
и скриншот `pin.png` сохраняются в `DATA_DIR/diagnostics/pin-<время>/`.
При ошибке сохраняется `error.png`, если браузер ещё доступен; событие
`pinterest-pin-failed` указывает, удалось ли получить скриншот.

## Полный обход и скачивание

```sh
npm start -- bootstrap
npm start -- sync
npm start -- sync --full
```

Обе команды выполняют один полный алгоритм в headless-браузере. `--full`
фиксируется в диагностике, но не меняет обход; известный Pin ID не останавливает
его. До sync требуется явная инициализация истории: завершённый bootstrap
без скачивания либо первоначальный backfill. SQLite сохраняет источники, файлы
и очередь с дедупликацией Pin ID/SHA-256; baseline и известные файлы обычный sync
пропускает. Backfill, resume и управление очередью — в [корневом README](../../../README.md).
Настройки MAX не требуются.

`board.ts` накапливает значения карточек, переживая виртуализацию DOM, и возвращает
`BoardPin`: Pin ID, URL, наблюдённые signature/адреса изображения либо ошибку материала.
Источник сохраняется независимо от пригодности изображения. Читается только основная
сетка `board-feed → base-board-pin-grid → masonry-container`, без вложенного
`more-ideas-feed`. Результат упорядочен по слотам доски.

`complete` требует стабильного подтверждённого счётчика, всех уникальных слотов
`0…count−1` и Pin ID, `aria-busy=false` основной сетки и появления `more-ideas-feed`.
Рекомендации не становятся источниками. Повторяющиеся экраны не доказывают конец.
За 120 секунд без подтверждения возвращается `partial` с уже прочитанными пинами
и причиной. Смена счётчика, принадлежности, доски, потеря доступа или структуры
тоже не выдаются за полный обход; нулевой или неизвестный счётчик не подтверждает
даже пустую доску.

`pin.ts` открывает каждый подтверждённый источник напрямую, без нового обхода.
Pin ID, точный URL, единственное изображение и signature должны совпасть.
Варианты берутся только из наблюдённых `src`, `currentSrc`, `srcset` карточки
и страницы пина. Разрешены HTTPS-адреса `i.pinimg.com` того же изображения;
URL `originals` не конструируется. Неподтверждённые видео/карусели дают отказ.

`image.ts` скачивает все наблюдённые варианты через Playwright, запрещая любые
перенаправления. Проверяются HTTP 200, фактический URL, MIME, `Content-Length`
при наличии, сигнатура и завершённость контейнера JPEG/PNG/WebP, затем декодирование
через браузерный `createImageBitmap`. Максимум выбирается по реальному числу
пикселей, а не по имени URL. Отказ любого варианта не разрешает тихо взять миниатюру.
Файл сохраняется в `DATA_DIR/images/<sha256>.<jpg|png|webp>` через приватный UUID `.part`,
повторное чтение и проверку SHA-256, затем атомарное переименование. Уборка `.part`
выполняется по возможности; такой файл никогда не считается готовым.

Успешный результат содержит источник, использованный `imageUrl`, локальный путь,
SHA-256, MIME, байты, размеры и проверенные варианты. `failed` содержит источник
и причину. `ready` результата относится к файлу; уникальное задание создаёт
хранилище. Принятие файла MAX этим не подтверждается. SHA-256 сравнивает байты;
перекодированные визуальные копии могут иметь разные хеши. Одинаковые байты
получают одно имя файла и не более одного задания.

`sync.ts` связывает обход, подготовку файлов и хранилище импорта без правил
будущего расписания. Внутренняя логика `core/` должна оставаться независимой
от Playwright и селекторов Pinterest.

## Результат команды и диагностика

В `DATA_DIR/diagnostics/sync-<время>-<UUID>/` сохраняются `sources.json` после
возврата обхода, `results.jsonl` по мере обработки материалов и `summary.json`.
Событие `pinterest-sync-finished` содержит тот же итог: `status`, `full`,
`traversalStatus`, `traversalReason`, `expectedCount`, `observed`, `ready`, `known`,
`materialFailures`, `browserFailures`, `unprocessed`, `browserStop` и путь диагностики.
При ошибке предпринимается попытка сохранить `error.png`;
`screenshotAvailable` явно показывает её результат.

Код 0 выдаётся при `status=complete`: подтверждён конец доски и условие режима
(bootstrap без скачивания, backfill до N, sync без отказов материалов). Код 1 — неполный результат или ошибка запуска. Ошибки материала
сохраняются и не мешают следующим пинам; CAPTCHA, потеря входа или неподтверждённая
структура останавливают дальнейшие браузерные действия. Полный обход источников
может сопровождаться неполным импортом файлов; уже сохранённые результаты остаются.

Отдельные live-проверки в видимом браузере:

```sh
node --env-file-if-exists=.env scripts/check-pinterest-board.ts
node --env-file-if-exists=.env scripts/check-pinterest-image.ts
```

Первая проверяет только обход и сохраняет `board-<время>/{board.json,board.png}`.
Вторая готовит изображение первого пина, повторно проверяет SHA-256 и декодирует
сохранённые байты; результат — `image-<время>/{image.json,decode.json,pin.png}`.
Каталоги находятся в `DATA_DIR/diagnostics/`; при ошибке скрипты пытаются сохранить
`error.png`. Эти операции используют тот же профиль и ownership DATA_DIR, что и CLI.
Сначала остановите run, idle или другой изменяющий процесс. Просмотр очереди
и справка доступны без захвата.

## Периодический запуск

После явного `bootstrap` или полного первоначального `backfill`, настройки MAX
и привязки канала через `auth max` команда `npm start -- run` запускает независимые
циклы импорта и пополнения MAX. Она не выбирает историю за пользователя;
медленный или приостановленный MAX не блокирует импорт Pinterest.
`SYNC_INTERVAL_SECONDS` по умолчанию 300; допустимы 0.001..2147483.647 секунды.
Доказанная временная сеть допускает до пяти повторов с растущей задержкой,
не раньше интервала и минимум через 5 секунд, с пределом таймера Node.js
2147483647 мс. Успешный цикл сбрасывает серию. DOM-таймаут сам по себе
не доказывает сетевой отказ.

Исчерпание повторов, потеря входа, CAPTCHA или неизвестный UI приостанавливают
только Pinterest; очередь и работа MAX сохраняются. Остановите `run`, исправьте
сеть, файл/диск или UI; при потере доступа выполните `auth pinterest`, затем
перезапустите `run`. Ошибка файла не является основанием для повторного входа.
Защита сайтов не обходится. SIGINT/SIGTERM прекращают новые операции, прерывают
браузер, сохраняют известный итог до диагностики и закрывают ресурсы.

Общий JSON `browser-error` содержит время, сервис, операцию, доступный jobId,
код, безопасную причину, путь диагностики и screenshotAvailable; screenshot
присутствует только при успехе, diagnosticWritten в логе сообщает итог записи
summary.json. Сырые cause, пароли, cookies и токены не сериализуются.
Ошибка диагностики не скрывает исходную ошибку; ошибка сохранения состояния
приостанавливает интеграцию до исправления. Подробный порядок восстановления —
в [корневом README](../../../README.md#рабочий-цикл-и-восстановление).

`run` проверен контролируемыми локальными тестами; live-worker с новыми
публикациями не запускался. Linux-контейнер и перенос авторизации проверены.
Сквозная проверка worker этапа 7.3 отменена пользователем из-за отсутствия
прав записи в исходную доску. Полная готовность MVP не подтверждена.

## Подтверждённые ограничения

На 6 ноября 2026 года реальная доска `mixi56453/max7` обойдена полностью:
166 уникальных источников, слоты 0–165, подтверждённый конец. Для пина
`632263235234925609` выбран наблюдённый `originals` 1289×1990; сохранённые байты
повторно декодированы и проверены по SHA-256. Реальный CLI `sync` до постоянной очереди обошёл 166/166
источников, сохранил семь изображений и завершился с кодом 1 из-за
`structure-changed` на восьмом пине; 158 источников остались необработанными.
При дополнительном чтении отказ не воспроизведён, точная причина не установлена.
Полный импорт всех файлов не подтверждён. Реальный отдельный запуск `--full`
не выполнялся; оба варианта CLI используют один алгоритм и проверены локально.

Локальный `run`, планировщик и MAX реализованы. Совместимость одного JPEG
с MAX проверена отдельно; перенос авторизации в Linux-контейнер подтверждён.
Поддержка всех файлов доски, реальные CAPTCHA и истечение сессии не подтверждены.
Локальные браузерные DOM/CLI-тесты требуют установленного Playwright Chromium
либо явного `PINTEREST_BROWSER_CHANNEL=chrome`; автоматической подмены нет.

Профили, cookies, токены и скриншоты — приватные данные. Новые каталоги создаются
с правами 0700, файлы диагностики и изображения — 0600 на POSIX-системах.
При записи общей диагностики права исправляются на 0700/0600;
права остальных существующих файлов не меняются. Храните их вне Git: стандартный `./data`
исключён через `.gitignore`; для другого каталога внутри репозитория добавьте
локальное исключение в `.git/info/exclude`. Не публикуйте диагностику или резервные копии.
