# Очередь публикаций

## Purpose

Хранить локальные задания и историю их обработки так, чтобы сбои, повторные команды и перезапуски не приводили к потере изображений или повторным постам.

## ADDED Requirements

### Requirement: Постоянное состояние задания

Сервис SHALL сохранять в локальной SQLite источник, ссылку на локальное изображение и его хеш, время добавления, статус, ошибки, назначенное время и известный результат создания поста.

#### Scenario: PQ-01 Сохранение и просмотр задания
- **GIVEN** изображение успешно подготовлено
- **WHEN** оно добавляется в очередь и затем приложение перезапускается
- **THEN** просмотр очереди показывает прежний источник, локальный файл, статус и время добавления
- **AND** известные ошибки, время планирования и сведения о созданном посте сохраняются

### Requirement: Единственное задание для источника и изображения

Сервис MUST исключать повторное задание по Pin ID и хешу изображения, включая ранее пропущенные и уже запланированные изображения.

#### Scenario: PQ-02 Дедупликация после завершения
- **GIVEN** задание с данным Pin ID или хешем уже запланировано либо пропущено
- **WHEN** импорт пытается добавить его повторно
- **THEN** сохраняется существующее задание без нового места в очереди
- **AND** история завершения не удаляется после исчезновения поста из отложки MAX

### Requirement: FIFO готовых заданий

Сервис SHALL выбирать готовые к безопасной обработке задания по времени добавления в очередь с устойчивым порядком при равном времени.

#### Scenario: PQ-03 Порядок обработки
- **GIVEN** в очереди есть несколько готовых заданий и задания, ожидающие повторной попытки или сверки
- **WHEN** освобождается слот публикации
- **THEN** выбирается самое раннее из готовых заданий
- **AND** отложенная ошибка одного задания не блокирует остальные готовые изображения

### Requirement: Единственный обработчик хранилища

Сервис MUST исключать одновременное выполнение изменяющих операций несколькими процессами в одном хранилище, включая CLI и фоновый процесс.

#### Scenario: PQ-04 Параллельный запуск
- **GIVEN** один процесс уже изменяет очередь или использует её браузерные профили
- **WHEN** второй процесс пытается запустить синхронизацию, bootstrap, backfill, планирование или изменение задания
- **THEN** второй процесс завершает команду с понятной ошибкой занятости
- **AND** не захватывает задание и не создаёт внешний пост

### Requirement: Восстановление с учётом внешнего побочного эффекта

Сервис MUST восстанавливать незавершённую обработку после перезапуска, различая безопасно повторяемый шаг и шаг, который уже мог создать пост в MAX.

#### Scenario: PQ-05 Перезапуск после возможного создания поста
- **GIVEN** процесс завершился после начала потенциально создающей пост операции, но до сохранения подтверждения
- **WHEN** приложение запускается снова
- **THEN** задание направляется на сверку с MAX без повторного создания
- **AND** уже подтверждённые задания остаются завершёнными независимо от текущего содержимого отложки

#### Scenario: PQ-06 Перезапуск до внешней отправки
- **GIVEN** подготовка была прервана до начала действия, способного создать пост
- **WHEN** приложение запускается снова
- **THEN** задание и локальный файл сохраняются и могут безопасно обрабатываться заново
- **AND** освобождаются только устаревшие локальные захваты, чей владелец достоверно завершился

### Requirement: Пропуск и безопасный повтор задания

Сервис SHALL позволять пропуск ещё не отправленного задания и повторную обработку исправимой ошибки без изменения исходного порядка и обхода защиты от дубликатов.

#### Scenario: PQ-07 Пропуск
- **GIVEN** задание ещё не отправлялось в MAX и сейчас не обрабатывается
- **WHEN** пользователь пропускает его через CLI
- **THEN** оно исключается из автоматического планирования с сохранением источника, файла и истории
- **AND** повторная синхронизация не возвращает его в очередь

#### Scenario: PQ-08 Повтор после определённой ошибки
- **GIVEN** задание завершилось исправимой ошибкой и достоверно не создало пост
- **WHEN** пользователь запрашивает повтор после устранения причины
- **THEN** задание возвращается к соответствующему безопасному шагу с исходным порядком и историей попыток
- **AND** повторно переданная команда не создаёт второе задание

#### Scenario: PQ-09 Повтор неопределённого или завершённого задания
- **GIVEN** задание уже запланировано, находится в процессе отправки либо имеет неопределённый результат
- **WHEN** пользователь запрашивает повторную обработку
- **THEN** завершённое или обрабатываемое задание не отправляется заново
- **AND** неопределённое задание допускает только сверку; отсутствие доказательства не заменяется принудительным повтором

### Requirement: Сохранение данных при ошибке MAX

Сервис SHALL сохранять исходное изображение, назначение и диагностические сведения при ошибке MAX для безопасного восстановления.

#### Scenario: PQ-10 Ошибка MAX до отправки
- **GIVEN** локальное изображение готово, но MAX недоступен до начала действия создания поста
- **WHEN** попытка завершается ошибкой
- **THEN** файл, источник и история ошибки сохраняются
- **AND** следующая безопасная попытка использует существующее задание и повторно рассчитывает допустимость будущего слота
