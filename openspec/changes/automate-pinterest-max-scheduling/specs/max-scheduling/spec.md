# Работа с отложкой MAX

## Purpose

Создавать отложенные публикации изображений в одном существующем канале MAX через веб-интерфейс с подтверждением результата и безопасной обработкой неопределённости.

## ADDED Requirements

### Requirement: Достоверное чтение отложки канала

Сервис SHALL получать через веб-интерфейс полный актуальный список отложенных постов выбранного существующего канала, включая ручные публикации, с датами и временем.

#### Scenario: MX-01 Чтение отложки
- **GIVEN** пользователь имеет доступ к настроенному каналу и его отложке
- **WHEN** сервис выполняет сверку
- **THEN** он получает все ожидающие посты, включая элементы вне первого экрана и посты, созданные вручную
- **AND** количество и время постов доступны планировщику

#### Scenario: MX-02 Неполное чтение или неверный канал
- **GIVEN** полный список не удалось прочитать либо открытый канал не совпадает с настроенным
- **WHEN** запрошено создание публикаций
- **THEN** сервис не создаёт посты на основании неполных или чужих данных
- **AND** сохраняет причину остановки и диагностику

### Requirement: Отложенный пост из локального изображения

Сервис SHALL загружать подготовленное локальное изображение в выбранный канал, создавать пост без текста на заданное будущее время и подтверждать его наличие в отложке.

#### Scenario: MX-03 Изображение поставлено в отложку
- **GIVEN** изображение готово, канал проверен, выбранное время свободно и лимит отложки не исчерпан
- **WHEN** сервис создаёт отложенный пост через веб-интерфейс
- **THEN** в отложке обнаруживается соответствующий пост с изображением, без текста и с ожидаемыми датой и временем
- **AND** задание сохраняет подтверждение и доступную устойчивую ссылку или идентификатор поста
- **AND** создание отложки не объявляется фактической публикацией; в назначенное время публикует MAX

#### Scenario: MX-04 Отклонение изображения до создания
- **GIVEN** MAX явно отклоняет файл или время до создания поста
- **WHEN** сервис получает достоверный результат отказа
- **THEN** задание сохраняется с конкретной ошибкой без отметки об успешном планировании
- **AND** повтор допустим только после устранения причины и повторной проверки отложки

### Requirement: Последняя проверка перед созданием

Сервис MUST повторно проверять канал, занятость выбранного времени и доступный объём отложки непосредственно перед действием создания поста.

#### Scenario: MX-05 Ручной пост появился после расчёта
- **GIVEN** расчёт выбрал свободный слот, но до финальной проверки пользователь занял его вручную
- **WHEN** сервис проверяет слот перед созданием
- **THEN** этот слот не используется и задание остаётся доступным для следующего подходящего слота
- **AND** ручной пост не меняется и не удаляется

### Requirement: Неопределённый результат не повторяется вслепую

Сервис MUST сохранять неопределённость, если пост уже мог быть создан, и исключать повторное действие создания для этого задания до достоверного разрешения результата.

#### Scenario: MX-06 Потеря ответа после создания
- **GIVEN** действие создания поста уже могло выполниться
- **WHEN** истёк таймаут, пропала сеть, сессия или процесс завершился до подтверждения
- **THEN** задание остаётся в неопределённом состоянии с изображением, целевым каналом и запрошенным временем
- **AND** последующие циклы и команды повтора не создают второй пост

### Requirement: Сверка неопределённой операции

Сервис SHALL разрешать неопределённый результат только по достоверным данным веб-интерфейса; отсутствие видимого поста само по себе не является доказательством неуспешного создания.

#### Scenario: MX-07 Однозначное подтверждение созданного поста
- **GIVEN** задание имеет неопределённый результат, а веб-интерфейс позволяет достоверно связать с ним один отложенный пост
- **WHEN** выполняется сверка канала, изображения и запрошенного времени с доступной устойчивой идентичностью
- **THEN** сохраняется подтверждение существующего поста без повторной загрузки и создания

#### Scenario: MX-08 Отсутствие или неоднозначность доказательств
- **GIVEN** пост не найден, время уже прошло или совпадение нельзя установить однозначно
- **WHEN** выполняется сверка неопределённого задания
- **THEN** сервис сохраняет неопределённость и сообщает о необходимости ручного разбора
- **AND** не делает вывода, что пост не создавался, только из-за его отсутствия в отложке

### Requirement: Работа только через веб-интерфейс

Сервис MUST выполнять планирование через браузерный интерфейс MAX без прямого обращения к MAX API или сторонним сервисам автоматизации.

#### Scenario: MX-09 Отсутствие обязательной возможности веб-интерфейса
- **GIVEN** доступный веб-интерфейс не позволяет создать отложенный пост или проверить его результат
- **WHEN** выполняется исследование или операция планирования
- **THEN** соответствующая возможность считается неподтверждённой или недоступной и операция прекращается
- **AND** сервис не подменяет её API, немедленной публикацией или фиктивным успешным результатом
