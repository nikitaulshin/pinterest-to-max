# Проектирование MVP Pinterest → MAX

## Context

Мотивация и границы продукта описаны в [proposal.md](proposal.md). Текущая архитектура — [README](../../../../README.md#архитектура), действующий доменный контекст — [docs/agents/domain.md](../../../../docs/agents/domain.md). Сейчас `src/main.ts` открывает пустое SQLite-хранилище и ожидает сигнал; браузерных интеграций, CLI и таблиц очереди нет. Существующие директории интеграций переиспользуются, агентские инструкции и исходный `CONTEXT.md` не переписываются.

Этот документ задаёт подход к реализации, а не результаты исследования сайтов. Требования находятся в шести `specs/*/spec.md`. Условие создания design выполнено: изменение затрагивает несколько модулей, постоянное состояние и согласование локальных транзакций с внешним действием.

## Goals / Non-Goals

**Цели проектирования:** сохранить малое число компонентов; сделать очередь восстанавливаемой; явно разделить безопасный повтор и возможное внешнее создание; получить проверяемые вертикальные результаты до массового запуска.

**Технические границы:** локальная файловая система одного узла, один пользователь и один канал. Нет распределённых блокировок, брокера, ORM, HTTP-сервера, универсальной системы плагинов, автоматического удаления истории или распознавания визуальных дубликатов. Неподтверждённая возможность веб-интерфейса не заменяется другой интеграцией.

## Decisions

### 1. Компоненты внутри существующего приложения

```text
CLI / main
  +--> Pinterest browser --> image downloader --> SQLite + local images
  +--> queue / planner -----------------------> MAX browser
  +--> runtime loops / diagnostics -----------> local diagnostics
```

| Область | Ответственность |
| --- | --- |
| `src/main.ts`, минимальный CLI | Разбор команд стандартными средствами Node.js, конфигурация, блокировка хранилища, запуск и завершение |
| `src/core/` | Жизненный цикл задания, правила очереди, чистый расчёт слотов и координация шагов; без Playwright и селекторов |
| `src/integrations/pinterest/` | Авторизация, обход доски, метаданные пина и адреса доступных изображений |
| `src/integrations/max/` | Авторизация, полное чтение отложки, заполнение формы, создание и подтверждение |
| Минимальный модуль локального хранения | SQLite-транзакции, миграции и файлы; без общей ORM или универсального repository |
| Небольшие функции диагностики | JSON-события и приватные скриншоты с общей идентичностью операции |

Выбор: существующий TypeScript/ESM, Node.js 24, Playwright и `node:sqlite`. Альтернативы — сервер БД, очередь Redis, веб-панель и фреймворк CLI — не нужны одному процессу. Публичная поверхность доменных объектов ограничивается поведением и необходимым доступом к состоянию по `AGENTS.md`; универсальные интерфейсы интеграций заранее не создаются.

### 2. Конфигурация и CLI

Настройки читаются из окружения/`.env` существующим способом. У каждой команды только относящиеся к ней обязательные настройки: импорт не требует доступного MAX. Имена будущих переменных и команд фиксируются здесь как контракт реализации:

| Настройка | Решение |
| --- | --- |
| `DATA_DIR` | Существующий каталог; внутри БД, изображения, два профиля и диагностика |
| `PINTEREST_BOARD_URL` | По умолчанию `https://ru.pinterest.com/mixi56453/max7`; одна доска на хранилище |
| `MAX_CHANNEL_URL` | Обязательно для авторизации MAX и планирования; значение должен предоставить пользователь, канал не угадывается |
| `PUBLICATION_SLOTS` | Обязательный список уникальных `HH:mm` через запятую, например `09:00,15:00,21:00`; пример не выбирает расписание за пользователя |
| `PLANNING_HORIZON_DAYS` | Положительное целое, по умолчанию `14` |
| `MAX_SCHEDULED_LIMIT` | Обязательный положительный предел общей отложки; допустимое значение подтверждается исследованием веб-интерфейса до массового запуска |
| `SYNC_INTERVAL_SECONDS` | Положительный интервал, по умолчанию `300`; сетевые ошибки увеличивают паузу, а не частоту обращений |

Часовой пояс фиксирован: `Europe/Moscow`, отдельной настройки нескольких зон нет. Даты в SQLite — UTC с однозначным преобразованием для отображения и браузера. Расчёт использует календарные правила этой зоны средствами Node.js, а не часовой пояс хоста или неявный разбор строки даты. Горизонт заканчивается в тот же московский момент через N календарных дней; граница включается, начало — строго в будущем. Требуемый MAX минимальный запас времени определяется на этапе 4 и применяется дополнительно.

Минимальные команды: `auth pinterest`, `auth max`, `sync [--full]`, `bootstrap`, `backfill --count N [--resume ID]`, `queue list`, `queue skip ID`, `queue retry ID`, `plan --dry-run`, `run`. Они вызываются через общий entry point npm/Node.js; окончательные команды запуска описываются в README при реализации. `backfill` выдаёт ID сохранённой операции; `--resume` продолжает именно её исходный лимит. Новый вызов без `--resume` — новый явный запрос следующей порции подходящей истории.

Отдельная команда массовой отправки не нужна: её выполняет `run`. Проверка одного реального поста на этапе 4 использует внутреннюю операцию с явными тестовыми входами, а не постоянный дополнительный режим продукта. `queue retry` не содержит принудительного обхода неопределённости: для такого задания доступна только сверка, затем отказ при отсутствии доказательств. `queue skip` разрешён для неотправленного `ready`/`failed`; `scheduled`, `submitting` и `uncertain` он не изменяет. Восстановление пропущенных заданий в MVP не предусматривается.

### 3. Модель данных

Следующая схема — минимальная логическая модель; конкретные SQL-колонки уточняются без изменения этих инвариантов. Версии схемы хранятся в SQLite и применяются до рабочего цикла.

| Данные | Минимальное содержимое и ограничения |
| --- | --- |
| `board_state` | URL доски, зафиксированная идентичность настроенного канала после его подключения, признак завершённой инициализации, время последнего успешного полного обхода. Смена доски или канала в непустом хранилище отклоняется; для другого контекста используется другой `DATA_DIR` |
| `pins` | Уникальный Pin ID, URL пина, выбранный image URL, первый/последний момент обнаружения, признак истории/кандидата, ссылка на изображение после скачивания, стадия и ошибка импорта |
| `images` | Уникальный SHA-256 байтов, относительный локальный путь, тип, размер и размеры изображения; одно изображение может иметь несколько Pin ID |
| `queue` | Устойчивый ID/порядковый номер, уникальный хеш изображения, исходный Pin ID, время добавления, состояние, время назначения, следующая попытка, последняя ошибка и подтверждённая ссылка MAX |
| `attempts` | ID попытки, задание, канал, хеш, запрошенное время, стадия, результат и диагностика. Намерение сохраняется до действия, которое уже может создать пост |
| `sync_runs` | ID, режим, запрошенное количество backfill, уже принятые задания, прогресс обхода, результат. Нужен для возобновления первоначальной истории и ограниченного backfill |

Сведения о полученном списке MAX живут в памяти одного цикла: полный список не дублируется в отдельную постоянную сущность. Все известные задания и попытки остаются в БД после выхода поста из отложки; автоматической очистки «надгробий» дедупликации нет.

Файл сначала скачивается в `.part` под `DATA_DIR/images`, проверяется и хешируется, затем атомарно переименовывается в имя на основе SHA-256 на том же файловом разделе. Только после этого короткая SQLite-транзакция связывает источники и создаёт единственное задание. Сбой после переименования до транзакции оставляет переиспользуемый файл, а не готовое задание с отсутствующими байтами. Недописанный `.part` не загружается в MAX. Перед отправкой проверяются существование и хеш файла; пропажа/повреждение даёт определённую локальную ошибку.

Для записанных данных вводятся ограничения уникальности Pin ID и хеша задания. `BEGIN IMMEDIATE` сериализует каждое изменение состояния; сетевые ожидания не входят в транзакцию основной БД. SQLite работает в WAL с внешними ключами, поэтому `queue list` может читать согласованный снимок параллельно с обработчиком.

### 4. Единственный владелец хранилища

Все изменяющие команды, авторизация, dry-run с браузером и `run` сначала удерживают эксклюзивную SQLite-транзакцию в отдельном небольшом `DATA_DIR/worker-lock.sqlite` до завершения команды. Основная БД состояния остаётся независимой и может фиксировать намерение отправки до обращения к MAX. Второй процесс немедленно получает понятную ошибку занятости. Чтение очереди не требует этого захвата и не запускает миграции.

Это локальная блокировка SQLite, освобождаемая ОС при смерти владельца. Её нельзя «просрочить» и передать другому живому процессу. Файл не удаляется при освобождении и не пересоздаётся поверх используемого inode. Альтернатива — lease с TTL/PID — создаёт риск двух владельцев после паузы процесса; файловый флаг без надёжного снятия зависает после аварии. Отдельный SQLite-файл использует уже выбранную библиотеку без новой зависимости. Поддержка NFS и нескольких узлов исключена.

### 5. Состояния и жизненный цикл

```text
pin discovered --> baseline (bootstrap only)
       |
       v
download + validation --> unique image --> ready --> preparing --> submitting
       |                                  |             |             |
       v                                  v             v             +--> scheduled
 import error                          skipped        failed          |
                                                        |             +--> uncertain
                                                        v                    |
                                                      ready                  +--> scheduled (proof)
                                                                             +--> uncertain (no proof)
```

`baseline` — классификация пина, а не статус задания. Bootstrap не требует скачивания всей истории: хеш появляется только для фактически полученных файлов. Дедупликация хешем охватывает скачанные изображения, дедупликация Pin ID — всю зарегистрированную историю. Backfill может выбрать baseline-пин, у которого ещё нет задания; обычная синхронизация этого не делает.

| Состояние задания | Значение и восстановление |
| --- | --- |
| `ready` | Проверенный локальный файл, можно назначать ближайший слот |
| `preparing` | Проверка канала/списка, резерв будущего слота и подготовка формы, про которые доказано, что они не создают пост. После аварии можно вернуть в `ready` |
| `submitting` | Намерение надёжно записано; действие уже могло создать пост. При аварии всегда переходит в `uncertain` |
| `uncertain` | Только сверка; ни сетевые повторы, ни `queue retry`, ни перенос времени не создают новый пост |
| `scheduled` | Создание подтверждено в MAX и подтверждение записано. Состояние терминальное; это не подтверждение фактического выхода |
| `failed` | Определённая ошибка до внешнего создания либо достоверный отказ MAX; безопасный повтор возможен после устранения причины |
| `skipped` | Терминальный ручной пропуск неотправленного задания; источник, файл и хеш сохраняются |

FIFO означает `(время добавления в queue, устойчивый порядковый номер)` среди готовых и уже разрешённых к повтору заданий. Ошибка или сверка не удерживает остальные готовые элементы. Повтор не переписывает этот порядок и не удаляет историю попыток. Ошибки скачивания остаются у источника и возобновляются синхронизацией; они не занимают слот готовой очереди.

### 6. Синхронизация Pinterest

1. Открыть заданную доску сохранённым браузерным контекстом, проверить доступ и ожидаемый интерфейс. Через DOM/наблюдаемое браузерное представление получить Pin ID и URL; прямых запросов к Pinterest API нет.
2. Загружать следующие элементы прокруткой. Собирать устойчивые Pin ID, не полагаясь на сохранение DOM-узлов при виртуализации; отделять подтверждённые элементы доски от рекомендаций и рекламы. Первоначальный и `--full` обход не заканчивается на известном пине. Обычный периодический обход в MVP использует тот же полный алгоритм: раннее завершение по «уже видели» не вводится без доказанной модели сортировки доски.
3. Завершение подтверждать обнаруженным при исследовании признаком конца/согласованной полноты списка. Одна пауза или несколько одинаковых экранов не являются достаточным доказательством. Есть ограничение времени операции и диагностика неполного обхода; частичные результаты сохраняются, признак полной инициализации — нет.
4. Bootstrap регистрирует наблюдённые Pin ID как историю без новых заданий, не меняет уже существующие задания. Первоначальный backfill обходит всю историю, принимает до N уникальных подходящих изображений в порядке обхода от начала, остальное регистрирует как baseline. Частичный запуск сохраняет ID операции; его возобновление не выбирает ещё N поверх уже принятого.
5. Backfill после bootstrap выбирает исторические пины без существующего задания. Дубликаты хешей и неподходящие материалы не расходуют N; недобор явно отражается в результате. Обычная синхронизация выбирает только впервые обнаруженные не-baseline источники и незавершённые допустимые импорты.
6. Для кандидата открыть представление пина и определить доступные варианты изображения. Выбрать наибольшее подтверждённое разрешение; не конструировать предположительный URL «originals» по шаблону и не считать миниатюру исходником без проверки. Если необходимый вариант нельзя достоверно получить, сохранить диагностируемую ошибку.
7. Скачать байты через Playwright, используя наблюдённый адрес изображения и при необходимости браузерную сессию. Запрос к CDN изображения допустим, прямой вызов Pinterest API — нет. Проверять HTTPS, допустимый источник/перенаправления, тип и декодируемость изображения; ограничения размера/формата уточняются по MAX, файл не обрезается молча.
8. Атомарно сохранить файл и данные; уникальный хеш переиспользует прежнее задание, а новый Pin ID добавляет только связь источника. Хеш побайтовый; перекодированные визуальные копии могут считаться разными. Изображения не редактируются ради обхода ограничений MAX.

Первый `sync`/`run` при неинициализированной истории отказывает и предлагает bootstrap/backfill. Пины, обнаруженные во время первоначального полного обхода, входят в его исторический набор; сервис не обещает восстановить фактическое время сохранения пина, если Pinterest его не показывает.

### 7. Планирование и работа с MAX

1. Без готовых заданий не создавать посты. Если есть `uncertain`, отдельная сверка может идти и без готовых элементов.
2. Открыть именно настроенный канал, проверить доступ, полностью прочитать отложку, включая ручные посты и даты вне горизонта. Неполнота списка запрещает новые записи MAX.
3. Сначала сверить `uncertain`. Подтверждение допустимо при ровно одном совпадении канала, запрошенной даты и времени и достоверно проверенного изображения в полном актуальном списке. Внешняя ссылка/ID необязательны и сохраняются, если доступны. Совпадения только по минуте, позиции, адресу media src либо числу постов недостаточно; отсутствие проверки изображения и несколько совпадений оставляют `uncertain`. Отсутствие записи, особенно после её предполагаемого выхода, не доказывает отсутствие создания. Неоднозначность остаётся в `uncertain` для ручного разбора; автоматического принудительного возврата в `ready` нет.
4. Посчитать ёмкость: эффективный подтверждённый лимит минус все актуальные отложенные посты и не покрытые ими потенциальные создания `uncertain`/`submitting`. Неидентифицируемое возможное совпадение можно консервативно учесть повторно, уменьшая ёмкость. Подтверждённые записи `scheduled` повторно поверх найденного списка не прибавляются.
5. Сгенерировать слоты от текущего московского момента до включительной границы горизонта. Отбросить прошлое и недопустимо близкое MAX время. Считать занятой всю минуту ручного/сервисного поста и сохранённого неопределённого назначения. Сопоставить готовые элементы FIFO свободным слотам до исчерпания горизонта или ёмкости.
6. В dry-run показать актуальный расчёт и причины исключений, не писать бизнес-данные, файлы изображений или посты. Эксклюзивный операционный захват и обновление браузером собственной сессии не считаются сохранением назначения. Это снимок, не резервирование будущего запуска.
7. Для настоящей отправки выполнять задания последовательно. Непосредственно перед действием повторно проверить канал, полноту списка, минуту и ёмкость; изменение занятости приводит к новому расчёту, не к перезаписи ручного поста.
8. Сохранить `preparing` и предварительный слот. До первого действия, которое по исследованному интерфейсу уже может создать пост, зафиксировать `submitting` и попытку с каналом, хешем и временем. Если загрузка сама способна отправить пост, граница проходит до загрузки, а не перед предполагаемой кнопкой подтверждения.
9. Через проверенную форму загрузить локальное изображение, оставить текст пустым, задать дату/время, создать отложку. Подтвердить однозначное совпадение канала, даты/времени и изображения в списке и сохранить доказательства; сохранить внешнюю ссылку/ID, если доступны. Если невозможно подтвердить материал/время, не помечать задание успешным.
10. При любом сомнении после границы создания записать `uncertain`. Следующее задание можно обрабатывать только после свежей полной сверки и консервативного учёта неизвестной операции. При сдвиге неотправленного назначения в прошлое пересчитать его; `uncertain` так не переносится.

У MAX нет общей с SQLite транзакции и подтверждённого ключа идемпотентности. Гарантия — отсутствие слепых повторов сервисом, а не безусловная доставка «ровно один раз». Ручное изменение отложки между последней проверкой и созданием остаётся внешней гонкой: после создания выполняется сверка, при коллизии дальнейшие записи приостанавливаются с диагностикой; ручные посты сервис не удаляет. Для воспроизводимой проверки массового режима пользователь не редактирует отложку в критический момент.

### 8. Браузерные сессии, ошибки и фоновый цикл

Сохраняются существующие пути `profiles/pinterest` и `profiles/max`. `auth` запускается локально с видимым Chromium и проверяет целевой ресурс, затем закрывает контекст. В Docker основной процесс headless. До запуска контейнера авторизация переносится в соответствующие подкаталоги его постоянного тома при остановленных процессах; переносимость локального профиля на Linux проверяется отдельной задачей. Если профиль несовместим, подбирается проверенный экспорт поддерживаемого состояния браузера в те же приватные каталоги либо ручной вход с графическим окружением на хосте запуска. Профиль не признаётся переносимым без реального запуска в контейнере; GUI/VNC-сервис автоматически не добавляется.

Фоновый процесс содержит два независимых асинхронных цикла: импорт и последовательное планирование MAX. У каждого собственный браузерный контекст, ограниченные ожидания и обработка ошибки. Неудача/долгое ожидание Pinterest не задерживает цикл готовой очереди MAX. Основная SQLite меняется короткими транзакциями без `await` внутри. Команды не создают отдельную очередь задач или распределённые воркеры.

| Ошибка | Действие |
| --- | --- |
| Временная сеть до возможной отправки | Сохранить причину и следующую попытку, экспоненциально увеличивать паузу до ограниченного максимума; конкретные интервалы покрыть проверкой с управляемым временем |
| Истёкшая сессия/CAPTCHA | Приостановить затронутую интеграцию до ручного входа, не обходить защиту; другая интеграция продолжает безопасную работу |
| Изменившийся интерфейс | Остановить затронутые действия, сохранить скриншот и контекст, продолжение после исследования и исправления; не угадывать селектор |
| Достоверный отказ MAX | `failed` с сохранением файла и возможностью безопасного повтора после исправления |
| Любая ошибка после возможного создания | `uncertain`, только сверка |
| Ошибка записи БД/нехватка диска | Не начинать новые внешние создания без надёжного намерения; сохранить доступную диагностику, остановить затронутые изменения |

Исправимая сетевая ошибка может автоматически вернуть `failed` в `ready` после сохранённого времени следующей попытки. Ошибка формата, авторизации или интерфейса такого перехода не запускает: нужна устранённая причина и явный безопасный повтор/возобновление. `submitting` и `uncertain` этим механизмом не затрагиваются.

JSON-логи: время, уровень, сервис, операция, ID запуска/попытки/задания, код ошибки и путь к диагностике. Cookies, токены, коды входа и URL с секретными параметрами не логируются. Скриншоты пишутся в `DATA_DIR/diagnostics` с приватными правами и относятся к исключённым из Git данным. Если страница/браузер умерли, отсутствие скриншота явно фиксируется; нельзя обещать снимок после аварийного завершения браузера.

SIGINT/SIGTERM запрещает новые операции, останавливает циклы и закрывает контексты. Возможная отправка сохраняется для сверки; при SIGKILL ту же защиту даёт предварительно записанный `submitting`. После завершения освобождается блокировка. Сервис не очищает изображения и историю автоматически.

### 9. Проверки и критерии доказательства

Чистый расчёт времени и переходы состояний проверяются `node:test` с управляемым временем. Пользовательские сценарии и аварии проверяются через публичный CLI с изолированным `DATA_DIR` и контролируемыми браузерными страницами/заменами только на границе интеграции. Отдельных тестов подключения БД, библиотек и wiring нет. Один сценарий — один тест; assertions и ошибки тестов на английском.

Локальные проверки не доказывают возможности живых сайтов. Реальные селекторы и сценарии записываются только после наблюдения; fixture без секретов проверяет известный контракт, но не заменяет реальную проверку. Для каждого внешнего этапа нужен журнал: дата, сервис, входные данные, выполненная команда, фактический результат, приватный путь к доказательствам. Тестовая отложка MAX требует явно выбранных канала, изображения и будущего времени с планом уборки до фактической публикации. Без этих входов внешняя проверка отмечается заблокированной, а не успешной.

## Risks / Trade-offs

- Отсутствие планировщика/чтения полной отложки в MAX → этап 4 проверяет обязательные действия до массовой реализации; невозможность блокирует этап 5 без API-обхода.
- Невозможность надёжной идентификации после сбоя → `uncertain` сохраняется; безопасность от дублей важнее автоматического продвижения конкретного задания.
- Невозможность доказать конец доски → частичный результат и повторное исследование, без ложного завершения bootstrap.
- Хеш байтов не распознаёт перекодирование → ограничение явно документируется, перцептивная дедупликация не входит в MVP.
- Ручная правка MAX в момент отправки → последняя проверка и контроль после создания, остаточная гонка отмечается явно.
- Профиль macOS может не работать в Linux → отдельная проверка переноса до завершения контейнерного этапа; дополнительные сервисы не предполагаются.
- Один владелец всего хранилища → mutating CLI и `auth` требуют остановки фонового процесса; просмотр очереди остаётся доступным.
- Полный периодический обход потенциально дорогой → ограниченные ожидания и настраиваемый интервал; оптимизация раннего завершения отложена до реальной необходимости.

## Migration Plan

1. До первой миграции остановить процесс и сохранить копию `DATA_DIR`; существующий пустой SQLite-файл и профили не удалять. Версионированная миграция создаёт таблицы атомарно и повторно не обнуляет данные.
2. Настроить доску, канал, слоты и подтверждённый лимит; вручную авторизоваться. Выполнить bootstrap либо первоначальный backfill до запуска `run`.
3. Проверить dry-run, одиночную тестовую отложку и ограниченную реальную партию. Массовый режим допускается только после закрытия внешних критериев этапов 1 и 4.
4. В Compose переиспользовать существующий постоянный том для БД, файлов, профилей и диагностики; не добавлять порты, веб-панель или сервис БД.
5. Откат программы выполняется при остановленном процессе. После возможных внешних созданий запрещено восстанавливать старую БД и просто повторять очередь: сначала сверить MAX и сохранить журнал попыток/дедупликацию. Если безопасный откат данных не доказан, оставить автоматизацию остановленной и исправлять вперёд. Отложенные посты MAX существуют независимо от отката кода и сами от него не отменяются.

## Проверки реализуемости перед зависимыми этапами

Эти проверки запрошены пользователем как часть вертикальной реализации и не являются предположениями о работающих сайтах. Они могут блокировать зависимые задачи; изменение требований вместо подтверждения требует отдельного согласования.

| Проверка | Способ и доказательство | Зависимый этап |
| --- | --- | --- |
| Реальные Pin ID, загрузка доски, максимальное изображение, признак конца | Видимый Playwright на заданной доске; метаданные одного реального пина, сравнение вариантов и полный обход | 1 → 2, затем 3 |
| Планировщик MAX и права целевого пользователя | Ручной вход Playwright, проверка канала, загрузка одного изображения без текста, время, подтверждённый пост в отложке | 4 → 5 |
| Полнота списка, однозначное совпадение канала/времени/изображения | Отложка с несколькими ручными/тестовыми постами и загрузкой элементов вне экрана; записать доказательства сопоставления и случаи, которые остаются неопределёнными | 4 → 5/6 |
| Лимит отложки, точность и зона времени, минимальный запас, допустимые файлы | Доступные подсказки/валидация веб-интерфейса и безопасный тест; не создавать десятки постов ради поиска лимита | 4 → 5 |
